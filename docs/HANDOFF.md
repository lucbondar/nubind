# Nubind: notas para retomar el proyecto

Documento para quien (persona o IA) retome el desarrollo sin el historial anterior. Describe el sistema de actualizaciones, que es la parte más delicada.

## Qué es
App Android (Kotlin + Jetpack Compose, Material 3 Expressive) más un módulo KernelSU que monta FTP, Google Drive y S3 con rclone como una carpeta del almacenamiento interno.

## Sistema de actualizaciones

**Canal:** `update.json`, publicado por el CI en el release fijo `updates`:
`https://github.com/lucbondar/nubind/releases/download/updates/update.json`
También lo lee KSU mediante `updateJson` en `module/module.prop`.

**Campos de update.json:**
- Módulo: `version`, `versionCode`, `zipUrl`, `changelog`
- App: `appVersion`, `appVersionCode`, `apkUrl`, `apkSha256`
- Módulo (para el flasheo desde la app): `zipUrl` (ya existía) y `zipSha256` (nuevo; el CI arma el zip antes de escribir update.json)

**Versiones (CI, `.github/workflows/build.yml`):**
- `build-app` fija `APP_VERSION_CODE = run_number + 100`.
- `package-module` usa la misma fórmula y estampa en `module.prop` las claves `appVersion` y `appVersionCode` (el APK que trae el módulo).
- Las dos fórmulas deben coincidir: si cambias una, cambia la otra.
- `app/build.gradle.kts` lee `versionCode` de `APP_VERSION_CODE` (local: 51). `versionName` se sube a mano.

**Firma:** el APK se firma con `debug.keystore` del repo. Si esa clave cambia, Android rechaza las actualizaciones sobre la versión instalada.

## Código

| Archivo | Rol |
|---|---|

| `assets/flash_module.sh` | Igual que `self_update.sh` pero para el módulo: `ksud module install <zip>` (o `magisk --install-module`), desacoplado porque `customize.sh` reinstala la app y mata el proceso; reabre la app al terminar |
| `assets/self_update.sh` | Instalador desacoplado de la app; reabre la app al terminar. Ambos scripts la reabren con el mismo intent del launcher (`am start -a MAIN -c LAUNCHER -f 0x10200000 -n ...`), no con `am start -n` a secas: así el intent raíz de la tarea coincide con el del launcher y al volver desde recientes/launcher no se apila una instancia nueva que arranque en Inicio (bug visto tras auto-actualizar app o módulo). Los scripts se leen de los assets de la app que está instalando, así que el arreglo se nota desde la actualización siguiente a la que lo trae. Va en la app, no en el módulo, porque el módulo instalado puede ser más viejo |
| `BindViewModel.kt` | `appUpdate`, `moduleNotice`, `checkForUpdates()`, `refreshUpdates()`, `installUpdate()`, `checkModuleSync()` (se llama desde `setRootGranted`), `dismissModuleNotice()` |
| `ui/components/UpdateBanner.kt` | `UpdateNotices()`, dentro de `HeaderCard` en `AboutScreen`. ## Comportamiento que no se debe romper
1. Al abrir la app busca actualización en silencio; sin red no muestra nada.
2. Con update disponible aparece "Actualizar ahora": con root instala sola, sin root abre `apkUrl` en el navegador.
3. Si el módulo KSU instalado trae un APK más viejo que la app, aparece un aviso: puede funcionar, pero para completar la actualización hay que descargar el módulo desde la app KSU. Botones "Descargar y flashear módulo" (`BindViewModel.flashModule()`: baja `zipUrl`, verifica `zipSha256`, flashea con root; no flashea si el módulo publicado trae una app más vieja que la instalada) y, debajo, el secundario tonal "Lo haré luego" (`dismissModuleNotice()`: se descarta hasta que cambie la versión de la app o del módulo). Ya no hay "Abrir KernelSU" ni "Entendido". Ya no existe la tarjeta "Estás al día" ni el botón de buscar de nuevo: si no hay actualización no se muestra nada (`AppUpdateState.UpToDate` se queda como estado interno). Ya no hay aviso emergente de desfase al abrir la app.
3b. Tras flashear, el módulo queda en `/data/adb/modules_update/nubind` hasta reiniciar: el aviso de desfase se reemplaza por una tarjeta verde "Módulo instalado" con botón "Reiniciar ahora" (`modulePendingReboot`) y, debajo, "Lo haré luego" (`postponeReboot()`): oculta la tarjeta y la cabecera verde y lo guarda en prefs (`KEY_REBOOT_POSTPONED`), así que persiste al salir de la app; la tarjeta no vuelve hasta tocar el chip "Reinicio pendiente" o flashear otro módulo. `checkModuleSync()` restaura el estado al abrir y lo borra cuando el reinicio ya no está pendiente. La UI usa `showRebootCard` (= pendiente y no pospuesto), no `modulePendingReboot` a secas. Mientras está pospuesto (`rebootReminder`) aparece una píldora fija "Reinicio pendiente" (verde) arriba a la derecha de la cabecera (`UpdateReminderChip`); al tocarla vuelve la tarjeta (`showRebootCardAgain()`). Igual con el desfase: si se pospone, `moduleNotice` queda en null pero `moduleBehind` sigue y la píldora ámbar "Módulo desfasado" (`moduleReminder`) vuelve a abrir el aviso (`showModuleNoticeAgain()`). Con una actualización de la app por instalar (`Available`, `Downloading`, `Installing` o `Failed` con reintento) el aviso de desfase no se dibuja: `BindViewModel.moduleNotice` es ahora un getter que devuelve null en ese caso (el valor real vive en `noticeCandidate`), así que queda solo la píldora ámbar y la cabecera se queda en verde. Si el usuario toca la píldora (`showModuleNoticeAgain()` pone `noticeForced`), la tarjeta aparece igual aunque haya actualización; "Lo haré luego" (`dismissModuleNotice()`) la vuelve a recoger. Nunca hay dos píldoras a la vez. `UpdateReminderChip` recuerda el último tipo visible (`lastKind`) para que, al tocarla, su salida animada no se redibuje con el texto/color del otro tipo (antes la verde mostraba un instante "Módulo desfasado").
3c. La búsqueda del arranque (`checkForUpdates`) corre una vez; después `refreshUpdates()` re-consulta en silencio (sin "Buscando…" ni errores) al volver a la app (`onResume`, máx. cada 30 s) y de inmediato al pulsar "Lo haré luego" (desfase o reinicio). Además `MainActivity` la repite cada 5 min mientras la app está a la vista (Handler en `onResume`/`onPause`). La búsqueda no depende del estado del módulo (desfasado, aviso pospuesto o reinicio pendiente) y se recupera de un fallo de red. También se busca (en silencio) al entrar a Acerca de, y deslizar hacia abajo ahí lanza una búsqueda manual (`checkForUpdates(manual = true)`, con "Buscando…" y aviso si falla): ya no hay botón de buscar. `AppUpdater.fetchLatest()` pide update.json con `?t=<ms>` y cabeceras no-cache para esquivar la caché de GitHub justo tras publicar, y cae a la URL normal si falla. No pisa descargas/instalaciones en curso.
4. Los módulos antiguos sin `appVersionCode` se comparan por número de versión (no detectan desfase entre builds de la misma versión).

## Changelog en el aviso de actualización
`UpdateInfo.changelogUrl` sale del campo `changelog` de update.json (el mismo `changelog.md` que lee KSU: el CI lo arma con `git log -n 15 --pretty='- %s'`, así que **el asunto de cada commit es lo que se ve**; conviene empezarlo con la versión, "2.5.42: ..."). En `UpdateBanner.kt`, con la actualización disponible, la píldora `ChangelogPill` ("Cambios") va a la derecha de "Actualizar ahora" y despliega `ChangelogList`, que baja el archivo la primera vez (`AppUpdater.fetchChangelog`, solo líneas "- ", máx. 10) y resalta la versión inicial en negrita. Sin `changelog` en update.json no aparece la píldora.

## Pantalla Logs
`ui/screens/LogsScreen.kt`: el texto se parsea en líneas (`parseLogEntries`: formato del módulo "Sun Oct 4 11:20:56 -03 2026: ..." y de rclone "2026/10/04 14:20:58 INFO : ...") y se dibuja en un `LazyColumn` con barra de color por severidad (error rojo, aviso ámbar, listo verde, info neutra; se clasifica por nivel de rclone o por palabras clave), hora tenue y mensaje en monoespaciada, más píldoras de resumen (líneas/errores/avisos). Desplazamiento rápido por gesto: sostener el dedo quieto ~0,3 s sobre el log (si se mueve más que el `touchSlop` antes, es un desplazamiento normal y no se toca) entra al modo rápido (`fast`, vibración corta). Después el log sigue el deslizamiento del dedo, sin importar en qué parte de la pantalla esté: dedo hacia arriba = el log sube, hacia abajo = baja. El recorrido se escala al largo de todo el log, no al de lo visible: deslizar el dedo por el alto completo del área táctil (`onSizeChanged` del `Box`) recorre el log entero. Factor = (tamaño medio de las líneas visibles + 4 dp de separación) * `totalItemsCount` / alto del área * `FAST_REACH` (1,15, margen porque las líneas no miden igual), mínimo 1. No hay curva ni aceleración propia: la velocidad del log es la del dedo por ese factor, así que la marca el ritmo del dedo (lento = lento, rápido = rápido). Se aplica con `listState.dispatchRawDelta` en cada evento; quieto no se mueve. El gesto es `pointerInput` en la pasada Initial: los primeros 0,3 s solo observa sin consumir; una vez en modo rápido consume los eventos para que la lista no se mueva con el dedo. Al soltar, el modo termina. Los botones flotantes ya no se tocan: `JumpIndicator` (flecha arriba/abajo) solo indica la dirección del último movimiento (`dir`, se apaga 160 ms después de parar); el activo se queda como aro vacío porque lo reemplaza una lupa real, `Modifier.magnifier` de Compose (lupa del sistema, API 28+; en versiones menores no se muestra), con el centro de la lupa 2 cm físicos por encima del dedo (`ydpi / 2,54 * 2`, sin salirse por arriba) y la fuente de la ampliación en ese mismo punto: muestra lo que hay donde está la lupa, no lo que tapa el dedo, zoom 1,8 y 96 dp redonda (tamaño/forma desde API 29). Sin dedo en modo rápido la fuente es `Offset.Unspecified` y la lupa se oculta. Sin logs el modo rápido y la lupa no se activan (el gesto no consume nada), y el estado vacío va dentro de una columna con `verticalScroll` para que deslizar hacia abajo siga lanzando la actualización de `ScreenContainer` (el `pullToRefresh` solo recibe el gesto si hay un hijo desplazable). Compartir sigue enviando `vm.logs` completo.

## Fluidez del desplazamiento del log
`LogRow` (en `LogsScreen.kt`) está escrita para desplazarse sin tirones; no la "embellezcas" con lo siguiente, que fue lo que se quitó en 2.5.64: **`height(IntrinsicSize.Min)`** (la barra de severidad con `fillMaxHeight` obligaba a medir cada texto dos veces; ahora la barra se dibuja con `drawBehind` y toma el alto de la fila), **`Modifier.clip(...)`** (cada fila creaba una capa propia; el tinte de error/aviso usa `background(color, shape)`, que no recorta) y **paletas por fila** (`syncAmberPalette()`/`updateGreenPalette()` se resuelven una vez en `rememberLogColors()` y se pasan como `LogColors`). `LogEntry` es `@Immutable`. La burbuja de `LogScrollbar` solo lee la geometría de la lista mientras está visible (`bubbleActive`); si no, se recolocaba en cada fotograma de desplazamiento. Sospecha pendiente, **sin tocar** porque cambia el aspecto: el vidrio esmerilado de la píldora (`hazeSource` sobre todo el pager en `MainActivity`) obliga a grabar el contenido de la pantalla otra vez en cada fotograma de desplazamiento; si aún se nota trabado, probar a desactivar el desenfoque (`blurEnabled`) mientras la lista se desplaza.

## Barra de desplazamiento del log
`LogScrollbar` (en `LogsScreen.kt`) se dibuja encima de la `LazyColumn`, solo con logs. Pulgar en píldora: aparece con resorte (`barShown`) al desplazar (`listState.isScrollInProgress`), en modo rápido o al arrastrarla, y también un instante al entrar a la pantalla; se oculta 1,3 s después de parar. Geometría en `LazyListState.thumbGeom()`: largo total estimado = tamaño medio de las líneas visibles * `totalItemsCount` (igual que el modo rápido), alto mínimo 48 dp, en los extremos (`canScrollForward/Backward`) llega siempre al borde; devuelve null (sin barra) si todo cabe. Se dibuja en `drawBehind` (lee el estado en la fase de dibujo, sin recomponer). Al sujetarla (`emphasized` = `barDragging || fast`) el pulgar pasa de 6 a 14 dp con rebote, se tiñe de `primary`, aparece una pista tenue y una burbuja `primaryContainer` "línea / total" a su izquierda, a la altura del pulgar (`Modifier.layout`). La franja táctil es de 28 dp (`ScrollbarTouchWidth`) y **solo tiene `pointerInput` mientras `shown`**: oculta, no intercepta nada y la lista se desplaza normal bajo ella. Arrastrar usa `detectVerticalDragGestures` y `dispatchRawDelta(dy * maxScroll / travel)` (dedo hacia abajo = hacia el final, como el modo rápido) y vibra con `SegmentTick` al empezar. El gesto de mantener-para-modo-rápido (`pointerInput` Initial del `Box` padre) **no arranca si el dedo cae en esa franja con la barra visible** (`barShown`), para que no compitan. La `LazyColumn` tiene 20 dp de `contentPadding` a la derecha para que el pulgar no tape el texto.

## Pestaña Logs: oculta por defecto
La pestaña Logs **viene oculta** (`BindViewModel.logsHidden` por defecto `true`, `KEY_LOGS_HIDDEN`; quien ya la había activado o desactivado a mano conserva su valor guardado). Se activa en Acerca de › Sistema › tarjeta **\"Mostrar Logs\"** (`ShowLogsToggle` en `AboutScreen.kt`, estilo expressive: toda la tarjeta es `toggleable` (con `.clip(shape)` antes: sin él el resplandor del toque se ve como un cuadro de esquinas rectas, también en `DontShowToggle`), el contenedor se llena de `primaryContainer` y las esquinas pasan de 20 a 32 dp con resorte, insignia `CookieBadge` que gira al estar activa, `Switch` con marca/cruz en el pulgar, vibración `SegmentTick`, subtítulo \"Visible/Oculta en la barra inferior\").

**Aviso de una sola vez:** `BindViewModel.updateLogsHidden(false)` muestra un `NoticeKind.Info` (`logs_mostrar_aviso`) explicando cómo desactivarla (interruptor o mantener 3 s el botón Logs) la primera vez que se activa, y guarda `KEY_LOGS_HIDE_HINT_SHOWN` en prefs para no repetirlo nunca más (ni al reactivarla ni al reabrir la app).

**Ocultar desde la pestaña Logs va directo a Inicio (2.5.66):** el gesto de la píldora (`FloatingPillNav`) deja de interpretar el dedo en cuanto salta el aviso de 3 s (`fired`: consume y `continue`, solo espera a soltar). Antes, al plegarse el botón Logs la píldora se reacomoda (se centra de nuevo) bajo el dedo quieto, la posición *local* del puntero cambia más que `touchSlop` y se tomaba por un arrastre que elegía la pestaña vecina (Acerca de) con `onSelect`, cancelando el `animateScrollToPage(0)` del viaje: se veía ir a Acerca de y luego saltar a Inicio. Además `setLogsVisible(false)` guarda `fromLogs`, completa el viaje a Inicio si algo lo interrumpió y fija `pendingScreen = Screen.Home` en ese caso. Ojo: las posiciones de ese gesto son locales a la píldora, que cambia de tamaño (etiqueta que aparece, botón que entra o sale); no compares nunca contra `down.position` esperando que sea estable.

**Segunda causa del mismo bug (2.5.67):** con lo anterior seguía pasando por Acerca de. Al soltar el dedo tras los 3 s, el `selectable` del botón Logs recibe el "arriba" **antes** que el gesto de la píldora (los hijos van primero en la pasada Main), así que el `consume()` del padre no cancela su clic y se ejecutaba `goTo(2)`; ese índice, al quitar Logs de `items`, pasa a ser Acerca de. Ahora `goTo()` devuelve sin hacer nada mientras `logsLeaving` está activo (`logsLeaving` se declara antes de `goTo`). No lo quites ni muevas la declaración después de `goTo`.

**Animación de salida/entrada del botón Logs (2.5.65):** `PillEntrance` pliega el botón **hacia su centro** (`shrinkTowards = CenterHorizontally/CenterVertically`; por defecto sería hacia el borde y el icono se veía barrido de lado) y el fundido de salida dura 280 ms, casi lo mismo que el pliegue. La fila/columna de la píldora usa `PillArrangement` (en `MainActivity.kt`) en vez de `Arrangement.spacedBy(4.dp)`: con `spacedBy` un botón plegado a tamaño 0 seguía dejando 4 dp de hueco fijo que desaparecía de golpe al quitar Logs de `items`, y la píldora (y el indicador, que rebota hacia sus nuevos límites) daba un tirón al final. `PillArrangement` escala el hueco que precede a cada botón según el tamaño de ese botón (completo a partir de 56 dp), así el hueco se cierra junto con él. Si cambias el alto/ancho mínimo de los botones de la píldora, cambia también el `56.dp` con el que se crea. Conocido y **sin tocar**: si Logs se oculta estando en Acerca de, esa página cambia de índice (3 -> 2) y se recompone de cero (pierde scroll y repite sus entradas); es lo aceptado por no poder usar `key` en el pager.

**Ocultarla de nuevo:** el mismo interruptor, o mantener presionado 3 s el botón Logs de la píldora (`LogsHideHoldMs`, gesto dentro de `FloatingPillNav`: solo cuenta si el dedo empieza sobre ese botón y no se arrastra; vibra al cumplirse y consume el resto del gesto para que soltar no abra la pestaña). **Sin diálogo de confirmación** (`HideLogsDialog` y los strings `logs_ocultar*` se eliminaron). Los dos caminos llaman a `setLogsVisible(false)` y **ocultan con animación**: `logsLeaving` hace que el botón Logs salga de la píldora (`PillEntrance` con `visible = false`: se desvanece, se encoge con `scaleOut` y se pliega con `shrinkHorizontally`/`shrinkVertically`, y la píldora se cierra con resorte); si el usuario está en Logs, a la vez la app viaja animada a Inicio. Pasados `LogsExitMs` (480 ms) y terminado el viaje, recién se llama a `updateLogsHidden(true)` (hasta entonces Logs sigue en `items`). Solo la pulsación larga deja además un aviso `Info` con la ruta de vuelta (`logs_ocultos_aviso`). `updateLogsHidden` se llama así y no `set…` porque `setLogsHidden` choca en la JVM con el setter privado de `logsHidden`.

**Al activar Logs desde Acerca de, la app viaja a la pestaña con animación:** `AppScaffold` tiene `setLogsVisible(visible)` (se entrega a `AboutScreen` como `onLogsVisibleChange`), que fija `pendingScreen` = pestaña actual (los índices del pager se corren al cambiar `items`; sin esto Acerca de saltaría a Logs sin animar) y, si se muestra, `goToLogs` + `logsEntering`. `LaunchedEffect(items)` primero devuelve al usuario a Acerca de (`scrollToPage`, instantáneo y sin que se note), espera 350 ms y hace `animateScrollToPage` a Logs: el indicador de la píldora se desliza hasta allí con su resorte (sigue a `pagerState.targetPage`). Mientras tanto el botón Logs entra con `PillEntrance` (resorte: crece desde el centro con `scaleIn`, se ensancha con `expandHorizontally`/`expandVertically` y se desvanece hacia dentro); solo anima con `logsEntering` (se apaga a los 1,5 s), así que al abrir la app o girar el teléfono el botón aparece ya en su sitio. Los límites de los botones (`bounds` en `FloatingPillNav`) se guardan **por pantalla** (`Map<Screen, Rect>`), no por índice: al quitar o añadir Logs los índices se corren y, con una lista por índice, el indicador parpadeaba a tamaño cero (y el gesto de arrastre usaba una lista vieja); el indicador además se queda en su último destino medido mientras un botón se re-mide. **No pongas `key` al `HorizontalPager`**: se probó en 2.5.57 (para conservar el estado de cada página cuando los índices se corren) y la app se cerraba al activar Logs; la clave lee `items[it]` y el pager puede evaluarla con el conteo de páginas nuevo y la lista vieja. Sin clave, al mostrar/ocultar Logs la página de Acerca de se recompone de cero (pierde scroll y repite las entradas), y es el comportamiento aceptado. `PillEntrance` lleva el `Modifier` de medición (`itemModifier`) en el contenedor de `AnimatedVisibility`, para que los `bounds` sigan en coordenadas de la fila/columna.

`AppScaffold` arma `items` según `vm.logsHidden` (sin Logs el pager tiene 3 páginas). Ocultar solo quita la pantalla: los logs siguen escribiéndose (scripts del módulo y rclone) y vuelven a leerse al mostrarla. Strings `logs_ocultos_aviso`, `logs_mostrar*` (`logs_mostrar`, `_on`, `_off`, `_aviso`) en los tres idiomas; `logs_pestana` ya no existe.

## Hoja "Nuevo servidor" (ServerSheet)
`ui/components/ServerSheet.kt`: `ModalBottomSheet` con un `AnimatedContent` que cambia el formulario según el tipo (FTP / Google Drive / S3). En servidor nuevo (`initial == null`) la columna usa `fillMaxHeight()`, así que la hoja mide siempre lo mismo. No lo quites: si el alto de la hoja cambia con la animación del formulario (`SizeTransform` con resorte), el `ModalBottomSheet` recalcula sus anclas cada fotograma y la hoja se desliza hacia abajo, rebota y deja el botón "Guardar servidor" cortado o un hueco arriba (bug visto al pasar de FTP a Drive y de Drive a S3). Al editar (`initial != null`) no hay cambio de tipo y la hoja se ajusta al contenido.

## Selector de carpetas: transiciones
`ui/components/FolderPickerDialog.kt`. Navegar entre carpetas ya no cambia la lista de golpe: la lista es un `AnimatedContent` con `targetState = current` (la carpeta). Entrar a una subcarpeta desliza la página nueva desde la derecha con fundido y la anterior sale hacia la izquierda; subir (o saltar a otra rama) va al revés (`folderNavDirection`: +1 si la carpeta nueva cuelga de la anterior). `SizeTransform(clip = true)` con resorte sin rebote acomoda la altura del diálogo en vez de saltar (sin rebote a propósito: el diálogo se redimensiona cada fotograma). La ruta (`pathPill`) cambia con un deslizamiento corto + fundido en el mismo sentido y la nota inferior (`infoNote`, raíz vs. subcarpeta) con fundido. **Cada página dibuja su propia carpeta**: el listado vive en `dirsByPath` (mapa ruta → lista), no en una sola variable; si fuera una sola, la página que sale mostraría de golpe el contenido de la carpeta nueva durante el deslizamiento. Las filas que llegan después de cargar entran con `animateItem()`. La caché (`FolderListCache`) y la apertura instantánea no cambian.
**Estabilidad (2.5.89):** tres causas de animaciones raras al entrar a ciertas carpetas, arregladas. (1) La lista de la hoja vertical medía `heightIn(max = 300.dp)`: al entrar a una carpeta **no visitada** la página nacía con el spinner (bajita) y, al llegar el listado con la transición ya terminada, el diálogo daba un salto de altura (y, al estar centrado, todo subía/bajaba); también al entrar a carpetas vacías o con pocas filas. ## Precarga: pausa
`preload.sh` mira el archivo `preload.paused` (en el directorio del módulo) antes de cada archivo: el que se está leyendo termina y los workers esperan. La app lo crea/borra con `RootShell.preloadPause()/preloadResume()`; `preloadStatus()` añade `"paused":true` al JSON si el archivo existe (`PreloadStatus.paused`). Botón en la tarjeta de Inicio (`BindViewModel.setPreloadPaused`) y acción en la notificación (`PreloadService`, acciones `PRELOAD_PAUSE/RESUME`). El script y `unmount.sh` limpian la bandera; los topes de seguridad (app y servicio) no corren mientras está en pausa.

## Reglas de trabajo
- **Cada cambio sube la sub versión** (2.5.4 -> 2.5.5), sin esperar a que lo pidan. Excepción: un cambio que solo toca este documento no sube la versión (ver la regla de confidencialidad más abajo). Va en tres sitios que deben coincidir: `versionName` en `app/build.gradle.kts`, y `version=v...` y `appVersion=...` en `module/module.prop`. El `versionCode` no se toca: lo fija el CI.
- **Se devuelve siempre el repo completo en un zip** (`nubind-<versión>.zip`, con la raíz del repo adentro: `app`, `module`, `docs`, `.github`, `debug.keystore`, etc.; sin `.git`, `build`, `.gradle` ni `*.apk`), no solo los archivos modificados. El usuario pasa el repo completo con `zip -r ... . -x ".git/*" "*/build/*" ".gradle/*" "*.apk"`.
- **Este documento es confidencial entre el usuario y Claude: nada de lo que tenga que ver con él puede aparecer en los commits** (ni en el asunto, ni en el cuerpo, ni en el changelog del aviso de actualización, que muestra los asuntos de los commits). Por eso, cuando un cambio solo toca este documento (una regla nueva, una corrección, una nota), **no sube la versión** y el commit lleva el mismo mensaje del último commit que cambió la app o el módulo (el asunto, tal cual, sin mencionar el documento), no uno propio. Si el cambio mezcla documento y código, el mensaje describe únicamente el código. En la respuesta se da el comando de commit ya con ese mensaje. Tampoco se escriben en commits, README ni código frases como «según el handoff» o «reglas de trabajo».
- **README:** al añadir o cambiar una función visible para el usuario, se actualiza `README.md` en la sección que corresponda (2.5.69 añadió «Tile de Ajustes rápidos» y el regreso directo a Inicio al ocultar Logs). Los arreglos internos (como el clip del resalte) solo van en este documento.
- **Release ("lanzar nuevo tag"):** el trabajo va en `preview`; para publicar se fusiona en `main` y se crea el tag `v<versión>`, que el CI publica como versión con nombre (`tags: ['v*']`). Cuando el usuario pide **"lanzar nuevo tag"**, la respuesta son **dos bloques de comandos**, uno por conjunto y en este orden, con la versión actual (`versionName`) en el tag. Ese pedido no cambia archivos: no se sube la versión ni se entrega zip.
  **Merge** (ejecutar cuando el CI de `preview` ya terminó bien):
  ```bash
  git checkout main
  git pull origin main
  git merge --no-ff preview -m "Merge preview: <versión>"
  git push origin main
  ```
  **Tag**:
  ```bash
  git tag -a v<versión> -m "Nubind <versión>"
  git push origin v<versión>
  git checkout preview
  ```
  El tag debe coincidir con `versionName` (por ejemplo `v2.5.69`).
- **Lo último de cada respuesta son los comandos para Termux**, apilados en un bloque, uno por línea, sin `cd`. Siempre estos cinco y en este orden: primero el `unzip` del zip entregado (se descarga del chat a `/storage/emulated/0/Download/`) hacia `/storage/emulated/0/Download/nubind/`, luego git, y `cinotif` al final:
  ```bash
  unzip -o /storage/emulated/0/Download/<zip entregado>.zip -d /storage/emulated/0/Download/nubind/
  git add -A
  git commit -m "<versión>: <resumen>"
  git push origin preview
  cinotif
  ```
  La rama de trabajo es `preview`.
  Excepción: `unzip -o` solo añade y sobrescribe, nunca borra (aunque el zip sea el repo completo). Si un cambio elimina o renombra archivos, se añade una línea `rm -f <ruta>` (sin `cd`, ruta desde la raíz del repo) justo después del `unzip` por cada archivo eliminado; si no, el repo conserva el archivo viejo y el CI lo compila (pasó con `BackupCard.kt` en 2.5.35: borrado en el zip, pero seguía en el repo y rompió la compilación).

## Termux: `cinotif` y `ciwatch`
Ambas son funciones del `~/.zshrc` del usuario (no están en el repo). `ciwatch` espera el run del commit con `gh run watch` y, si falla, guarda los logs en `~/storage/downloads/logs_<id>.zip`. **No se puede enviar su salida a `termux-notification` con una tubería**: `gh run watch` redibuja la pantalla en vez de imprimir líneas y el `while read` no recibe nada. Por eso existe `cinotif` (necesita el paquete `termux-api` y la app Termux:API con permiso de notificaciones): busca el run igual, pero consulta el estado cada 5 s con `gh run view --json status,conclusion,jobs` y actualiza una notificación fija (`--id ci`, `--ongoing`) con \"Paso N/M · <paso en curso>\". Al terminar bien muestra \"✅ Compilación exitosa\" con vibración; si falla, \"❌ Falló (<conclusión>)\", vibra y guarda los mismos logs en Descargas; con Ctrl+C quita la notificación fija (`always`). Se escribió sin poder ejecutarla: si algo falla, `ciwatch` sigue sirviendo. Para reinstalarla, pegar esto en Termux y `source ~/.zshrc`:
  ```zsh
  cinotif() {
    local br sha id i out st co done_n total cur t
    br=$(git branch --show-current)
    sha=$(git rev-parse HEAD)
    t="CI ${sha[1,7]}"
    echo "Esperando el run de ${sha[1,7]}..."
    termux-notification --id ci --title "$t" --content "Esperando el run..." --ongoing --alert-once
    {
      for i in {1..30}; do
        id=$(gh run list --branch "$br" --commit "$sha" --limit 1 --json databaseId -q '.[0].databaseId')
        [ -n "$id" ] && break
        sleep 2
      done
      [ -z "$id" ] && {
        echo "No apareció ningún run para este commit"
        termux-notification --id ci --title "$t" --content "No apareció ningún run"
        return 1
      }
      while true; do
        out=$(gh run view "$id" --json status,conclusion,jobs -q '[.status, (.conclusion // "-"), ([.jobs[].steps[]? | select(.status=="completed")] | length), ([.jobs[].steps[]?] | length), (first(.jobs[].steps[]? | select(.status=="in_progress") | .name) // "-")] | @tsv')
        if [ -z "$out" ]; then sleep 5; continue; fi
        IFS=$'\t' read -r st co done_n total cur <<< "$out"
        [ "$st" = "completed" ] && break
        echo "paso $done_n/$total · $cur"
        termux-notification --id ci --title "$t" --content "Paso $done_n/$total · $cur" --ongoing --alert-once
        sleep 5
      done
      if [ "$co" = "success" ]; then
        echo "Compilación exitosa"
        termux-notification --id ci --title "$t" --content "✅ Compilación exitosa" --priority high --vibrate 300,150,300
        return 0
      fi
      echo "Terminó con: $co"
      gh api "repos/{owner}/{repo}/actions/runs/$id/logs" > ~/storage/downloads/logs_$id.zip && echo "Logs guardados en ~/storage/downloads/logs_$id.zip"
      termux-notification --id ci --title "$t" --content "❌ Falló ($co). Logs en Descargas: logs_$id.zip" --priority high --vibrate 300,150,300
      return 1
    } always {
      [ "$st" = "completed" ] || [ -z "$id" ] || termux-notification-remove ci
    }
  }
  ```
  Con la pantalla apagada Android puede pausar Termux: usar `termux-wake-lock` o quitarle la restricción de batería.
